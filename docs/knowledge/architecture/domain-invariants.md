# Core Domain Invariants

All domain rules execute inside `@veyra/core` services backed by SQLite (`packages/core/src/db.ts` and `packages/core/src/schema.ts`). Refer to `packages/core/src/types.ts` for exact Zod schemas and field shapes; this document owns the behavioral invariants that code enforces across entities.

## Sync-Ready Storage Conventions

- **SQLite pragmas:** Every connection enables `WAL` journaling and `foreign_keys = ON`, running idempotent `CREATE TABLE IF NOT EXISTS` migrations at open time, plus additive `ALTER TABLE ... ADD COLUMN` steps guarded by `PRAGMA table_info` for columns added after a table shipped (`projects.match_keywords`).
- **Identity and soft deletes:** Core domain tables (`goals`, `projects`, `blocks`, `focus_sessions`, `calendar_events`, `daily_notes`, `weekly_reviews`) use UUID primary keys, ISO-8601 `updatedAt`, and nullable `deletedAt` soft deletes. `settings` is a singleton row (`id = 'default'`, no `deletedAt`); `activity_log` is append-only.
- **Soft-delete referential integrity:** Because soft-delete `UPDATE`s do not trigger SQLite `ON DELETE SET NULL`, services clean up references explicitly inside one transaction (`packages/core/src/services/goals-projects.ts`): `deleteGoal` nulls `projects.defaultGoalId`, `blocks.goalId`, `calendar_events.goalId`, and `daily_notes.goalId`, while `deleteProject` reassigns active `blocks` to the system `Other` project (`SYSTEM_OTHER_PROJECT_ID`) and nulls `calendar_events.projectId` and `daily_notes.projectId`. The system `Other` project cannot be deleted or archived (`SystemProjectError`).
- **Fractional ordering:** `goals` and `blocks` sort by lexicographic `orderKey` values generated by `packages/core/src/order-key.ts` so reordering touches one row.

## Entity Ownership And Orthogonal Model

- **System `Other` project:** Bootstrap seeds a non-deletable system project (`isSystem = true`) with a fixed UUID (`SYSTEM_OTHER_PROJECT_ID`). Unassigned blocks default to `Other` so UI and rollups avoid null project special-casing.
- **Orthogonal `Goal`, `Project`, and `Ops`:** `Project` answers where work lives, `Goal` answers why it matters, and `isOps` marks essential reactive work independently. A block, calendar event, or daily note can carry any combination of all three.
- **Derived `Quiet` projects:** A project is classified as `Quiet` dynamically when `max(lastFocusSessionEndedAt, lastBlockCompletedAt, createdAt)` is older than 7 days while its status remains `active`.

## Block Buckets And Scheduling Rules

- Blocks occupy one of three buckets: `inbox`, `scheduled`, or `later`.
- `scheduled` requires a date-only `scheduledDate` (`YYYY-MM-DD`). Optional `plannedStartAt` and `plannedEndAt` reserve a future calendar slot without turning `Plan` into rigid timeblocking.
- `later` requires a date-only `revisitAt` checkpoint (defaulting to 14 days out when parked without an explicit horizon). Moving a block out of `scheduled` clears `scheduledDate` and planned slot timestamps; moving out of `later` clears `revisitAt`.
- `dueDate` is always optional and date-only (never a clock time) for real external cutoffs only.

## Single Focus And Multi-Day Sessions

- At most one non-deleted `FocusSession` may have `endedAt = null` at any time. Starting or resuming a block automatically closes any previously running session at the same timestamp.
- Pausing closes the active session and optionally stores `resumeNote` on the block without changing `status`. Stopping closes the active session without modifying `resumeNote` or completing the block.
- Completing a block closes any active session for that block, marks `status = 'done'`, and records optional `energySignal` (`up`, `neutral`, `down`) and `outcomeNote`.
- A single block can accumulate multiple `FocusSession` rows across multiple days. `focused today` sums only the portion of each session overlapping the local calendar day in `Settings.timezone`, while block totals sum all non-deleted sessions for that block.
- Retroactive editing supports `log` (manual past session), `trim` (adjusting `startedAt`/`endedAt`), and `split` (dividing one session into two around an interruption gap of N minutes).

## Timezone Rollover And Guilt-Free Recurrence

- `Settings.timezone` (IANA string, defaulting to host timezone) anchors every local day and week boundary, even when the server runs in UTC Docker.
- Midnight rollover (`packages/core/src/services/rollover.ts`) is idempotent and transactional:
  - Unfinished (`status = 'todo'`) non-recurring `scheduled` blocks from earlier dates move silently to today and increment `carryoverCount` by 1.
  - Untouched past recurring occurrences (`status = 'todo'` with zero non-deleted focus sessions) are soft-deleted with zero carryover.
  - Active recurring series (`weekdays`, `days:[...]`, or `weekly`, linked by `seriesId`) materialize today's occurrence when the rule matches today and no row (active or soft-deleted) exists for `(seriesId, today)`. Stopping a series (`drop` with `stopSeries`) clears `recurrenceRule` so future occurrences stop generating.
- Weekly rule lookups shift across Monday-anchored week boundaries so a rule written during week N displays on `Today` throughout week N+1.
