# Core Domain Invariants

All domain rules execute inside `@veyra/core` services backed by SQLite (`packages/core/src/db.ts` and `packages/core/src/schema.ts`). Refer to `packages/core/src/types.ts` for exact Zod schemas and field shapes; this document owns the behavioral invariants that code enforces across entities.

## Sync-Ready Storage Conventions

- **SQLite pragmas and additive migrations:** Every connection enables `WAL` journaling and `foreign_keys = ON`, runs idempotent `CREATE TABLE IF NOT EXISTS` migrations at open time, and applies `PRAGMA table_info`-guarded `ALTER TABLE ... ADD COLUMN` steps so existing databases upgrade without data loss (`goals` specificity/closing columns, `projects.match_keywords` and `projects.weekly_time_minutes`, `blocks.size_minutes`/`sense_signal`/`drop_reason`, `weekly_reviews.previous_rule_kept`/`completed_at`/`snapshot_json`, and `settings` integration/hotkey columns).
- **Identity and soft deletes:** Core domain tables (`goals`, `projects`, `blocks`, `focus_sessions`, `calendar_events`, `daily_notes`, `weekly_reviews`) use UUID primary keys, ISO-8601 `updatedAt`, and nullable `deletedAt` soft deletes. `goal_measure_updates` stores append-only weekly measure history per goal (`ON DELETE CASCADE`); `settings` is a singleton row (`id = 'default'`, no `deletedAt`); `activity_log` is append-only.
- **Soft-delete referential integrity:** Because soft-delete `UPDATE`s do not trigger SQLite `ON DELETE SET NULL`, services clean up references explicitly inside one transaction (`packages/core/src/services/goals-projects.ts`): `deleteGoal` nulls `projects.defaultGoalId`, `blocks.goalId`, `calendar_events.goalId`, and `daily_notes.goalId`, while `deleteProject` reassigns active `blocks` to the system `Other` project (`SYSTEM_OTHER_PROJECT_ID`) and nulls `calendar_events.projectId` and `daily_notes.projectId`. The system `Other` project cannot be deleted or archived (`SystemProjectError`).
- **Fractional ordering:** `goals` (within the same `kind`) and `blocks` sort by lexicographic `orderKey` values generated by `packages/core/src/order-key.ts` so reordering touches one row.

## Entity Ownership, Goals Lifecycle, And Weekly Time

- **System `Other` project:** Bootstrap seeds a non-deletable system project (`isSystem = true`) with a fixed UUID (`SYSTEM_OTHER_PROJECT_ID`). Unassigned blocks default to `Other` so UI and rollups avoid null project special-casing.
- **Orthogonal `Goal`, `Project`, and `Ops`:** `Project` answers where work lives, `Goal` answers why it matters, and `isOps` marks essential reactive work independently. A block, calendar event, or daily note can carry any combination of all three.
- **Personal vs. Company goals and closing lifecycle:** Every goal carries a `kind` (`personal` or `company`; legacy rows default to `personal`), optional specificity fields (`description` "Why it matters", `doneWhen`, date-only `checkInDate`, `measure`, `ifItStalls`), and lifecycle status (`active`, `achieved`, or `archived` rendered as `Let Go`). Updating `measure` appends an audit entry to `goal_measure_updates`. Closing a goal (`closeGoal`) records `status` (`achieved` or `archived`), `closingNote`, and `closedAt`; both closed statuses are excluded from active pickers (`listGoals({ activeOnly: true })`) while preserving historical links on blocks, projects, and meetings.
- **Weekly time intentions belong exclusively to Projects:** `Project.weeklyTimeMinutes` is an optional non-binding weekly intention (never a hard cap or red alarm). `Goal` always reports measured focus and block outcomes with zero weekly hour targets.
- **Project variance & 8-week history:** `listProjects` and `getProject` derive weekly variance status (`over` > +20%, `under` < -20% with focus > 0, `untouched` when intent is set and focus is 0, `on_track` within ±20%, `time_without_plan` when unset and focus > 60m, or `unplanned`), 8-week weekly focus buckets, 8-week average, and learned size drift.
- **Derived `Quiet` projects:** A project is classified as `Quiet` dynamically when `max(lastFocusSessionEndedAt, lastBlockCompletedAt, createdAt)` is older than 7 days while its status remains `active`.

## Block Buckets, Scheduling, Sizing, And Drop Rules

- Blocks occupy one of three buckets: `inbox`, `scheduled`, or `later`.
- `scheduled` requires a date-only `scheduledDate` (`YYYY-MM-DD`). Optional `plannedStartAt` and `plannedEndAt` reserve a future calendar slot without turning `Plan` into rigid timeblocking.
- `later` requires a date-only `revisitAt` checkpoint (defaulting to 14 days out when parked without an explicit horizon). Moving a block out of `scheduled` clears `scheduledDate` and planned slot timestamps; moving out of `later` clears `revisitAt`.
- `dueDate` is always optional and date-only (never a clock time) for real external cutoffs only.
- Optional `sizeMinutes` (`30`, `60`, or `120`) captures a rough block size used strictly for capacity fit lines and `Plan` strips (never a countdown or quota); when unset, capacity calculations fall back to the project's learned default size.
- Dropping a block accepts an optional `dropReason` (`not_important`, `someone_else`, or `no_room`). Reopening a block to `todo` clears `dropReason`.

## Single Focus, Sense Check, And Multi-Day Sessions

- At most one non-deleted `FocusSession` may have `endedAt = null` at any time. Starting or resuming a block automatically closes any previously running session at the same timestamp.
- Pausing closes the active session and optionally stores `resumeNote` on the block without changing `status`. Stopping closes the active session without modifying `resumeNote` or completing the block. Cancelling discards the active session cleanly.
- Completing a block closes any active session for that block, marks `status = 'done'`, and records optional `energySignal` (`up`, `neutral`, `down`), `senseSignal` (`moved`, `partly`, `motion` — whether the block made sense for its goal), and `outcomeNote`.
- A single block can accumulate multiple `FocusSession` rows across multiple days. `focused today` sums only the portion of each session overlapping the local calendar day in `Settings.timezone`, while block totals sum all non-deleted sessions for that block.
- Retroactive editing supports `log` (manual past session), `trim` (adjusting `startedAt`/`endedAt`), and `split` (dividing one session into two around an interruption gap of N minutes).

## Capacity, Suggested Order, And Learning Engine

Deterministic capacity signals live in `packages/core/src/services/capacity.ts` so `@veyra/web` and `@veyra/cli` consume identical facts:

- **Weekday room (`computeWeekdayRoom`):** Median real focus time for that weekday across the prior 4 weeks minus today's non-deleted meetings, falling back to a 240-minute focus baseline minus meetings until at least 2 historical weekday samples exist.
- **Learned block size & drift (`computeProjectSizeStatsMap`):** Over an 8-week window, once a project has at least 3 completed blocks with focus sessions, its learned default size is the median actual duration snapped to `30`, `60`, or `120` minutes (otherwise `60` minutes), alongside its size drift ratio vs. planned sizes.
- **Fit line & suggested order (`computeTodayCapacity`):** Splits `UP NEXT` at cumulative `Room today` into fitting blocks and `Probably not today`. Ranks blocks deterministically with a one-line reason per item: real commitments (`dueDate` today/tomorrow or prep for a meeting today), then goal-linked work ordered by goal priority and projects behind `weeklyTimeMinutes`, then remaining non-Ops blocks, then `Ops` last. Learned adjustments sink blocks belonging to a project motion hotspot (`>= 3` sensed blocks and `>= 60%` `motion`, excluding the system `Other` project) and flag chronic carryovers (`carryoverCount >= 3`) for decision instead of promoting them. Never auto-reorders: `applySuggestedOrder` writes new `orderKey`s only on explicit user action.
- **Day look back:** Computed once today's `UP NEXT` clears (with at least one completed block today) or on first open the next morning, summarizing focused input, goal share, blocks that moved a goal, and items that did not fit.

## Timezone Rollover And Guilt-Free Recurrence

- `Settings.timezone` (IANA string, defaulting to host timezone) anchors every local day and week boundary, even when the server runs in UTC Docker.
- Midnight rollover (`packages/core/src/services/rollover.ts`) is idempotent and transactional:
  - Unfinished (`status = 'todo'`) non-recurring `scheduled` blocks from earlier dates move silently to today and increment `carryoverCount` by 1.
  - Untouched past recurring occurrences (`status = 'todo'` with zero non-deleted focus sessions) are soft-deleted with zero carryover.
  - Active recurring series (`weekdays`, `days:[...]`, or `weekly`, linked by `seriesId`) materialize today's occurrence when the rule matches today and no row (active or soft-deleted) exists for `(seriesId, today)`. Stopping a series (`drop` with `stopSeries`) clears `recurrenceRule` so future occurrences stop generating.
- Weekly rule lookups shift across Monday-anchored week boundaries so a rule written during week N displays on `Today` throughout week N+1.
